**Эксперт:** архитектор / ответственный за поддержку кода · **Оценка:** 3 / 5
**Дата:** 2026-11-01 · **Ветка:** `arena/7cdeb11b-slovo2` · **Итог:** [`00-summary.md`](./00-summary.md)

> **Мнение эксперта.** Ядро спроектировано правильно: логика отделена от React, у
> безопасности данных есть явная модель, а проверки написаны вокруг инвариантов, а не
> вокруг деталей интерфейса. Проблема в том, что продуктовая сложность растёт внутрь
> базовых типов и центральных файлов. Пока проект один, это терпимо. Как основа для
> второго проекта — это станет главным препятствием.

## 3. Находки

### A1. Центральный стор — монолит (высокий риск)

`src/state/store.ts` (2183 строки) объединяет: профили, уроки, награды, магазин,
покупки, музыку, сундуки, пазлы, списки, журнал сейфа, снимки, обновление, гидратацию,
сброс и импорт. Внутри — модульные переменные (`hydrationResetRevision`, `localResetRevision`),
которые управляют тем, какое чтение «актуально». Это работает, но понимать такой код
может только тот, кто его писал.

- **Почему важно.** Любой новый модуль (например, математические задания) добавит
  действия в тот же объект, и граница между «данными» и «поведением» исчезнет.
- **Рекомендация.** Разрезать на слайсы zustand (`profiles`, `progress`, `shop`,
  `settings`, `vault`, `ui`), каждый с собственным набором действий и тестами. Правила
  подсчёта — в чистых функциях `engine/`, стор только связывает их с состоянием.
  Модульные флаги заменить состоянием слайса или явным параметром.
- **Размер.** M–L (см. план, задача 1.3).

### A2. Экраны смешивают интерфейс и бизнес-правила (средний риск)

`ShopScreen.tsx` (2467 строк) содержит и разметку, и правила отображения цен, фильтров,
сдачи товара, тюнинга и «желаний». Часть правил уже вынесена в `engine/shop.ts`
(462 строки), но не вся. Тот же паттерн — в `LessonScreen` и `HomeScreen`.

- **Почему важно.** Правило нельзя проверить без рендера, поэтому тесты идут через
  jsdom и смоук. Это дорого по времени (см. A7) и хрупко при изменении вёрстки.
- **Рекомендация.** Правило «что показать и сколько стоит» — в `engine/` с юнит-тестом.
  Экран получает готовую модель и только рисует её. Разбить `ShopScreen` по разделам
  (наряды, техника, музыка, звуки, сундуки) — отдельные файлы.

### A3. Продукт вшит в базовые типы — главный блокер для шаблона

Это ключевой вывод для вашей цели.

- Тип `Word` (`src/types.ts`) описывает **словарь**: `stress` — индекс ударной буквы,
  `syllables`, `danger` — индексы «опасных» букв, `dangerKind`, `sentence` с пропуском.
  Всё это специфично для русской орфографии.
- `Profile` содержит **31 поле**, из которых большинство — функции магазина и геймификации:
  `shop`, `puzzle`, `chestSkin`, `buildings`, `customWords`, `lists`, `daily`, `weekly`…
- В `engine/` 17 модулей из 30 — продуктовые или словарные: `shop`, `buk-chat`, `naash`,
  `base-tours`, `base-sets`, `chests`, `puzzles`, `music`, `sounds`, `tints`, `buildings`,
  `world`, `rating`, `qr`, `qrPng`, `word-facts`, `dictionary`.
- Ядро обучения — `srs.ts` (107 строк), `adaptive.ts` (30), `scheduler.ts` (333),
  `quests.ts`, `study.ts`, `rewards.ts` — тоже знает о «словах» (`Word`, `WordState`, `LESSONS`).

- **Почему важно.** Для математики нужно заменить «слово» на «задачу» с параметрами
  (числа, операция, шаги решения). Сейчас для этого надо править типы, стор и экраны
  одновременно.
- **Рекомендация.** Ввести обобщённую сущность **`Item`** (id, навык, подсказки, теги,
  класс, произвольный `payload`). `Word` стал бы одним из видов `Item`. Продуктовые
  модули — опциональными плагинами с регистрацией, а не полями `Profile`.
- **Размер.** L (план, фаза 3).

### A4. Мёртвый и заменённый код (низкий–средний риск)

- **`src/ui/HangarScene.tsx` (178 строк) и `src/ui/TechScene.tsx` (169 строк) не импортируются.**
  Смоук-тест (`tests/smoke.test.tsx`, строка с «Мой мир») подтверждает, что ангар заменён
  экраном «Мой мир». Файлы остались, а `engine/shop.ts` всё ещё упоминает ангар
  в комментариях. Это вводит в заблуждение.
- **Демо-точки входа внутри `src/ui/`:** `CardDemo.tsx` (182) и `ShopDemo.tsx` (1185)
  подключены как отдельные HTML-страницы витрин в `vite.config.ts`. Это осознанно, но
  код витрин живёт рядом с продуктовым и попадает в сборку.
- **CSS.** Эвристика по `app.css`: ≈150 из ≈1000 классов не встречаются ни в одном файле
  `src/` (например `list-card-*`, `home-goal`, `streak-days` — проверено вручную). Часть
  классов может строиться динамически, поэтому точная цифра требует инструмента.
- **Рекомендация.** Удалить `HangarScene`/`TechScene` после подтверждения владельцем,
  перенести витрины в `demos/`, подключить инструмент поиска неиспользуемого CSS.
- **Размер.** S.

### A5. Процесс версий встроен в код и мешает (высокий риск для команды)

Правило из `README.md`: каждый PR повышает `version` в `package.json` и `package-lock.json`,
добавляет `docs/RELEASE-X.Y.Z.md` и ставит версию в заголовок PR. Проверяет это
`scripts/release-check.mjs` в CI. Подробности и цифры — в аудите 3 (R5).

- **Почему важно для архитектуры.** Версия — это общий файл, и при параллельных PR он
  становится точкой конфликтов. Правило «вручную» создаёт работу, которую легко
  пропустить: 9 из 30 последних проверок упали именно на нём.
- **Рекомендация.** Автоматизировать (release-please или changesets), не менять правило
  «каждое изменение — релиз», но убрать ручные шаги.

### A6. Документация пишется для агента, а не для людей (средний риск)

- `README.md` (919 строк) смешивает руководство для разработчика и **заметки о песочнице**
  («Грабля: рабочая копия пересоздаётся», «Урок PR #140»). Это полезно автору процесса,
  но не новому участнику.
- `docs/HANDOFF.md` (440 строк) — «точка передачи контекста» для ИИ-агента
  («не продолжать работу по старым чатам»).
- `docs/PLAN.md` (4995 строк) — журнал по частям 1–97.
- 151 файл `RELEASE-*.md`, не имеющий индекса.
- **Устаревшие цифры.** `README.md` пишет «~198 kB JS» (сейчас главный бандл 338 КБ),
  `docs/perf-audit.md` — precache 753 КиБ (сейчас 23 МиБ), комментарий в `vite.config.ts`
  говорит, что precache «должен оставаться маленьким», хотя он уже 23 МБ.
- **Рекомендация.** Разделить: `README` (что это и как запустить), `docs/ARCHITECTURE.md`
  (слои, инварианты, как добавить фичу), `CONTRIBUTING.md` (для людей), `CHANGELOG.md`
  (вместо 151 файла), служебные заметки агента — в отдельную папку. Цифры в документах
  либо генерировать, либо датировать.
- **Размер.** S–M.

### A7. Тестовая архитектура: широкая, но тяжёлая (средний риск)

**Сильная сторона:** покрытие широкое — юнит-суиты по движку, UI-проверки через
`react-dom` + jsdom, стенды для сейфа и покупок, контрастность, иконки, галереи,
проверка прод-бандла. Всё это запускается в CI.

**Слабые стороны:**

- **Нет тест-раннера.** Свой харнесс: функция `check(name, ok, detail)` и агрегаторы.
  `tests/adaptive.test.ts` импортирует 19 суитов, `tests/smoke.test.tsx` — около 25 UI-модулей.
  Падение одной проверки не даёт отчёта по имени теста в стандартном формате, а
  запуск одного файла требует знать агрегатор.
- **Монолит.** Смоук — 2140 строк и 148 секунд. Новый кейс легко сломать чужой.
- **Нет отчёта о покрытии** и порога для `engine/`.
- **Нет линтера и форматтера** (ни ESLint, ни Prettier, ни Biome). Правила стиля и
  границ слоёв держатся на договорённостях.

- **Рекомендация.** Перевести суиты на Vitest (или `node:test` с ясными именами),
  разбить смоук на сценарии, добавить покрытие и ESLint с правилом границ слоёв (A8).
- **Размер.** M.

### A8. Границы слоёв держатся на договорённости, а не на правиле

Сейчас «`engine/` не зависит от React и UI» — это правда, но не защищено. Ни одна
проверка не упадёт, если завтра кто-то импортирует `state/store` в `engine/`.

- **Рекомендация.** `eslint-plugin-boundaries` или `dependency-cruiser` с правилами:
  `engine` → только `engine`; `platform` → `engine`, `platform`; `state` → `engine`,
  `platform`, `state`; `ui` → всё, кроме `scripts`. Добавить в `check.yml`.
- **Размер.** S.

### A9. Репозиторий тяжёлый (низкий риск, растёт со временем)

- `git ls-files` — 88 МБ; `.git` — 79 МБ.
- В git лежат 12 MP3 (34 МБ) и сотни WebP, включая `docs/promo`, `docs/merch`,
  `docs/naash`, `public/products` (189 файлов), `public/cars` (57).
- Каждое обновление бинарника навсегда остаётся в истории.
- **Рекомендация.** Git LFS для аудио и крупных картинок, либо хранение артефактов
  вне репозитория с проверкой хешей (`check-audio` уже сверяет каталог и файлы). Для
  шаблона — обязательно: клон нового проекта не должен весить 88 МБ.
- **Размер.** M.

## 5. Что сделать в первую очередь (кратко, подробно — в плане)

1. Удалить мёртвый код и привести устаревшие комментарии (A4). *S*
2. Добавить правила границ слоёв (A8). *S*
3. Автоматизировать версии (A5) — снимает главный источник красного CI. *M*
4. Разрезать стор на слайсы и вынести правила из экранов (A1, A2). *M–L*
5. Ввести `Item` и перевести словарь на него (A3). *L*, после пункта 4.

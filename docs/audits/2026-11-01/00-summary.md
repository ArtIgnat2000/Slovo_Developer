## 1. Короткий вывод

СЛОВО 2.0 технически **заметно зрелее типичного учебного прототипа**. Чистое ядро
(`src/engine/` не импортирует React, `platform/`, `state/` и `ui/`), продуманная
защита прогресса детей, автоматические проверки контента и 1163 проверки в смоук-тесте,
которые проходят. Но **как базовый шаблон для других проектов (например, математики)
проект пока не готов**. Причин четыре:

1. **Продукт и движок переплетены.** Тип `Word` (ударение, слоги, опасные буквы),
   `Profile` (31 поле: магазин, БУК, сундуки, пазлы, музыка…) и `store.ts` (2183 строки,
   68 действий) — словарно-магазинные. Для математики придётся переписывать модель, а не
   подключать модуль.
2. **Доставка тяжелее, чем заявлено.** Precache собранного PWA — **568 файлов, ≈23 МБ**,
   хотя в комментариях `vite.config.ts` и в документации речь о «маленьком» precache и
   ~200 КБ JS. При установке ребёнок или родитель скачивает магазинные картинки и музыку
   до того, как открыт первый урок.
3. **Процесс мешает разработке.** Правило «каждый PR повышает версию + заметка + заголовок»
   красит **9 из 30** последних запусков PR-проверок — и все 9 упали на одном и том же шаге,
   а не на коде.
4. **Есть узкие места, которые вырастут вместе с данными.** Весь прогресс — один JSON-документ,
   который пишется в IndexedDB **при каждом** `set` (включая показ тоста). Сейчас это ≈1–1,5 мс
   на запись, но на объёме в ~15 раз больше — уже ≈18–23 мс (замер в `02-performance.md`, §2.5).

**Рекомендация:** не переписывать. Сначала **расчистить** (фаза 0, несколько дней), затем
**выделить ядро с жёсткой границей слоёв** (фазы 1–2), и только потом делать из репозитория
шаблон (фаза 3). Общий план — `04-action-plan.md`.

## 2. Мнения экспертов (оценки по шкале 1–5)

Три аудитора смотрели на проект со своих позиций. Оценки субъективны, но каждая
опирается на перечисленные в соответствующем аудите факты и команды.

| # | Аудит и роль эксперта | Оценка | Мнение одной фразой |
|---|---|:---:|---|
| 1 | **Архитектор / поддержка** (`01-architecture.md`) | **3** | Ядро `engine/` чистое и хорошо тестируется, но центральный стор и экраны выросли в монолиты, а продуктовые фичи вросли в базовые типы. Для шаблона — главный блокер. |
| 2 | **Frontend / PWA-производительность** (`02-performance.md`) | **2** по доставке, **3** по рантайму | Рантайм приемлем. Вес установки (23 МБ precache), отсутствие code-splitting и запись всего стора на каждое действие — слабые места, видны по коду и замерам. |
| 3 | **Надёжность, безопасность, DevOps** (`03-reliability-security-delivery.md`) | **4** | Лучшая часть проекта: защита прогресса от потери продумана, проверяется стендами и тестами; клиент без `innerHTML`/`eval`. Слабее — процесс релизов, деплой без полного гейта, dev-зависимость с уязвимостью. |

**Интегральная оценка:** **2,5 / 5 как основа для других проектов** и **4 / 5 как продукт
в текущем виде**. Разрыв между ними закрывается планом фаз 0–2.

### Внешние ориентиры, на которые опираются выводы

Мнения «со стороны» собраны по публичным первоисточникам, а не опросом людей:

- **Precache.** Chrome for Developers прямо предупреждает: precache слишком большого числа
  ресурсов тратит трафик пользователя и замедляет установку service worker; крупные ресурсы
  рекомендуется отдавать через runtime-кэш [1](https://developer.chrome.com/docs/workbox/service-worker-deployment).
- **Хранилище в Safari.** WebKit удаляет script-writable хранилище сайта (включая IndexedDB)
  после 7 дней использования без взаимодействия с сайтом; исключение — приложения,
  добавленные на домашний экран [2](https://progressivewebapps.com/platforms/ios-safari/).
  Это подтверждает, что главный риск потери данных у приложения — не код, а платформа.
- **`node:sqlite`.** Модуль Node.js остаётся в статусе release candidate (Stability 1.2);
  в последних версиях API уже менялся [3](https://cnayanajith.com/blog/node-sqlite). Для пилотного
  сервера это риск, а не блокер.

## 4. Что уже хорошо (не трогать без нужды)

- **Слои.** `engine/` не импортирует React, `platform/`, `state/`, `ui/` (проверено grep:
  совпадения только в комментариях). Это основа для переиспользования.
- **Защита прогресса.** Очередь записей, чтение до записи (заморозка при сбое чтения),
  три слота снимков, копия «до покупки», санитайзер импорта, журнал событий. Документ
  `docs/progress-loss-audit.md` разбирает восемь каналов потери и закрывает их.
- **Контент как код с проверками.** `check-content`, `contrast-check` (288 пар цветов, все ≥ AA),
  `icons-check`, `prod-boot-check` (ловит падение React #185 на прод-бандле). Такой подход
  нужен и для задач по математике.
- **Клиентская безопасность.** Ноль `innerHTML`, `eval`, `dangerouslySetInnerHTML`;
  внешние ссылки с `rel="noopener noreferrer"`; нет сторонних скриптов и аналитики.
- **Пилотный сервер.** Токены хранятся как SHA-256, сравнение через `timingSafeEqual`,
  лимит тела запроса 64 КБ, белый список событий телеметрии, текст ответов не хранится,
  Docker-образ запускается от непривилегированного пользователя.
- **PWA-обновления.** Применяются только в безопасный момент (не во время урока).
- **Прозрачность версии.** Версия и SHA коммита видны ребёнку и родителю — удобно для
  отладки «что у нас на сайте».

| `npm run typecheck` | ок | ≈10 с |

| `npm run test:content`, `test:adaptive`, `test:galleries`, `test:release`, `test:icons`, `test:contrast`, `test:guard` | ок | от 0,2 до 9 с |

Замеры состояния и синтетический бенчмарк записи — в `02-performance.md`.

### Чего не проверено (и почему это важно)

- **Реальные устройства и сеть.** Нет замеров на телефоне, Lighthouse и WebPageTest не
  запускались. Все цифры про **вес** — это размеры файлов из сборки, а не время загрузки.
- **Браузерное поведение.** Safari, eviction, service worker и квоты не проверялись.
- **Настройки защиты ветки `main`.** API вернул 403 (`Resource not accessible by integration`),
  поэтому, включены ли обязательные проверки, неизвестно. Владельцу репозитория стоит проверить это вручную.
- **Git-история** в этой песочнице неполная (shallow clone), поэтому динамика по времени
  из `git log` не использовалась; для динамики опирались на номера PR и журналы в `docs/`.
- **«Мнения экспертов»** — это три роли-аудитора, работающие по коду и измерениям, плюс
  публичные первоисточники. Это не опрос живых специалистов. Если нужен внешний ревью,
  его стоит заказать отдельно, с этими документами как входом.

### Воспроизведение ключевых замеров

```bash
npm run build && grep -o 'precacheAndRoute(\[.*' dist/sw.js | wc -c     # размер списка precache
npm audit --omit=dev && npm audit                                       # уязвимости prod / все
gh run list --workflow check.yml --limit 30 --json conclusion           # статистика PR-проверок
```

Синтетический бенчмарк (`JSON.parse` + `JSON.stringify` состояния разного размера) —
описан в `02-performance.md`, §2.5.

# План действий: техническая оптимизация и подготовка базового шаблона

**Дата:** 2026-11-01 · **Ветка:** `arena/7cdeb11b-slovo2` · **Основа:** аудиты 01–03 и [`00-summary.md`](./00-summary.md)

ID находок в плане совпадают с аудитами: **A** — архитектура (`01`), **P** — производительность (`02`),
**R** — надёжность, безопасность, доставка (`03`).

> **Принцип.** Сначала расчистить и измерить, потом выделять ядро, и только затем
> делать шаблон. Ни один пункт не должен ослабить защиту прогресса ребёнка: любое
> изменение записи проверяется `test:guard`, `audit:storage` и `tests/vault.test.ts`.

## 0. Цели и критерии успеха

| Цель | Сейчас | Цель после фаз 0–2 | Как измеряем |
|---|---|---|---|
| Precache при установке | 23,1 MiB, 568 файлов | ≤ 3 MiB | `dist/sw.js`, число записей |
| Первый JS (gzip) | ≈242 КБ (4 чанка) | −35…40 % (≈150 КБ) | визуализатор чанков |
| PR без падения из-за версии | 9 из 30 падений | 0 из 20 PR | `gh run list` |
| Нарушения границ слоёв | не проверяются | 0, проверяет линтер в CI | `eslint` / `dependency-cruiser` |
| Время смоука | 148 с | ≤ 60 с, либо распараллелен | `time npm run test:smoke` |
| Запись состояния на UI-действие | на каждый `set` | только при изменении данных | тест счётчика записей |
| Регрессии данных | закрыты стендами | + E2E в браузере на 4–6 сценариев | Playwright в CI |
| Ядро для шаблона | смешано с продуктом | отдельные пакеты, `Item` вместо `Word` | структура `packages/` |

Численные цели — предложение. Владелец подтверждает их после замеров на устройстве (P8).

**Оценки трудоёмкости** — ориентир для одного опытного разработчика: фаза 0 — 3–5 дней;
фаза 1 — 1,5–2 недели; фаза 2 — 3–4 недели; фаза 3 — 3–5 недель. Они не учитывают ревью и
согласования с владельцем.

## Фаза 0 — быстрые победы (3–5 дней)

Цель — снять самые заметные проблемы без изменения архитектуры.

### 0.1. Precache: только то, что нужно первому уроку — **P1** · *S*

- Исключить из precache: `products/`, `cars/`, `ships/`, `electronics/`, `planes/`,
  `buildings/`, `illustrations/`, `icons/` сверх минимума (через `globIgnores` в `vite.config.ts`).
- Оставить: оболочку, `words/`, минимальные иконки, стартовый трек (решение владельца, см. §6).
- Для остального — `runtime` `CacheFirst` с `maxEntries` по образцу `base-tours`, `naash`, `buk3d`.
- Убрать `maximumFileSizeToCacheInBytes: 12 MB`.
- **Приёмка:** precache ≤ 3 MiB; `test:galleries` и `test:boot` зелёные; ручной сценарий:
  установка → первый урок офлайн; магазин после первого открытия работает офлайн.
- **Риск:** магазин без картинок при первом открытии офлайн. Смягчение: runtime-кэш
  с предзагрузкой карточек, которые показываются первыми.

### 0.2. Не писать в IndexedDB при изменениях, не касающихся данных — **P2** · *S*

- В `persist` (или обёртке хранилища) сравнивать ссылки `profiles`, `activeId`, `settings`,
  `vault` и пропускать запись, если они не менялись (`toast`, `mascot`-состояние и т. п.).
- **Приёмка:** новый тест «показ тоста не вызывает `setItem`»; `test:guard`, `audit:storage`,
  `tests/vault.test.ts` без изменений результата.
- **Запрещено:** вводить debounce без тестов потери данных (`progress-loss-audit.md`).

### 0.3. Vite и dev-сервер по умолчанию — **R6** · *S–M*

- Обновить `vite` до версии с исправлением high-уязвимости; проверить совместимость
  `vite-plugin-pwa` и `@vitejs/plugin-react`.
- `server.host` и `preview.host` — `localhost` по умолчанию; сеть — только по флагу
  (`VITE_LAN=1`); `allowedHosts` для туннелей — тоже по флагу.
- Превью для песочницы (`preview:show`) сохранить рабочим.
- **Приёмка:** `npm audit` без high в dev; `npm run build`, `test:smoke`, `test:boot`; превью в песочнице открывается.

### 0.4. Мёртвый код и витрины — **A4** · *S*

- **Приёмка:** `typecheck`, `build`, `test:smoke` зелёные; размер `main` не вырос.

### 0.5. Полный контур перед деплоем — **R4** · *S*

## Фаза 3 — базовый шаблон (3–5 недель)

Цель — из этого репозитория получить шаблон, на котором можно поднять проект по другому
предмету (например, математике), не копируя словарь и продуктовые фичи.

### 3.1. Структура пакетов — **A3** · *M*

Монорепозиторий (npm workspaces), без смены хостинга:

```
packages/
  core-learning/     SRS, адаптивность, планировщик, Item (из engine/srs, adaptive, scheduler)
  core-progress/     сейф, очередь, снимки, миграции, схемы (engine/vault, platform/storage, platform/vault)
  core-pwa/          обновления, precache-политика, установка (platform/pwa, vite-плагин)
  core-gamification/ задания дня, награды, недели (quests, rewards, weekly-rewards) — опционально
  core-quality/      release-check, check-content (обобщённый), contrast, icons, boot-check
  ui-kit/            токены, базовые компоненты (Bits, Icon — после очистки)
apps/
  slovo2/            словарный продукт: контент, словарь, магазин, БУК, сервер-пилот
  template-math/     пример второго предмета (см. 3.4)
```

- **Приёмка:** `apps/slovo2` собирается и проходит все проверки без изменения поведения;
  пакеты не импортируют друг друга в обход правил (1.2).

### 3.2. Обобщить `Word` в `Item` — **A3** · *L*

- Ввести `Item`: `id`, `skill`, `prompt`, `answer` (или генератор), `hints`, `tags`, `grade`,
  `payload` (произвольные данные предмета).
- `Word` — один из видов `Item` (`kind: 'word'`), с полями ударения и опасных букв в `payload`.
- Правила проверки ответа — стратегии (`exact`, `normalized`, `numeric`, `steps`), выбираются предметом.
- `check-content` становится общим валидатором с правилами из пакета предмета.
- **Приёмка:** все 257 слов работают как `Item` без изменения результатов `test:content`
  и `test:adaptive`.

### 3.3. Продукт — как опциональные модули — **A3, A1** · *M*

- Регистрация модулей: `shop`, `mascot/buk`, `naash`, `base-tours`, `chests`, `puzzles`,
  `music`, `rating`. Каждый модуль — свой слайс и свои UI-точки входа.
- Предмет выбирает набор модулей в конфигурации (`project.config.ts`, см. R10).
- **Приёмка:** `template-math` собирается без магазина и словаря; `slovo2` — с полным набором.

### 3.4. Пример: шаблон для математики — **цель шаблона** · *L*

Минимальный проверяемый результат, а не полный продукт:

- 20 задач 1 класса (сложение и вычитание в пределах 20), генерируемые по параметрам,
  а не из фиксированного банка.
- Один урок, SRS, награды, сейф прогресса, PWA, офлайн.
- Проверка ответов: числовая; шаги решения — стратегия `steps` (можно отложить на следующий этап).
- Контент-валидатор для задач: ответ совпадает с генератором, нет дубликатов параметров.
- **Приёмка:** `template-math` проходит общие гейты (`release-check`, `boot-check`, E2E 2.3)
  и один живой сценарий «пройти урок и получить награду».

### 3.5. Процесс «создать проект из шаблона» — **A6, R10** · *S–M*

- Скрипт `npm run new:project -- --name=math --subject=math` — копирует `apps/template-math`,
  переименовывает пакеты, заполняет `project.config.ts`.
- `CONTRIBUTING.md` описывает, что менять при новом предмете (чек-лист из 10 пунктов).
- **Приёмка:** новый проект поднимается за один час человеком, не знакомым с кодом.

## 4. Порядок и зависимости

```
Фаза 0 ──► Фаза 1 (1.1 версии первой) ──► Фаза 2 (2.1 миграции до 2.2) ──► Фаза 3
             │                                   │
             └─ 1.2 границы ─► 1.3 слайсы ────────┴─ 2.3 E2E нужен до 2.2 и 1.3
```

- **1.1 (версии)** — первый, иначе каждый PR из фаз 0–3 будет падать на ручном шаге.
- **1.2 (границы)** — до 1.3, иначе слайсы «протекут».
- **2.1 (миграции)** — до 2.2 и до любого изменения формы `Profile`.
- **2.3 (E2E)** — до 2.2 и 1.3: без него регрессии данных не поймать в браузере.
- **3.x** — только после 2.1 и 1.2.

## 5. Риски и что не делать

| Что не делать | Почему |
|---|---|
| Переписывать проект с нуля | Защита данных и тесты — ценность, которую нельзя потерять |
| Debounce записи без тестов потери | Прямо запрещено в `progress-loss-audit.md` и `perf-audit.md` |
| Удалять precache ради скорости без замеров | Сначала замер на устройстве (2.6), потом решение |
| Менять сейф без `test:guard` и `audit:storage` | Это единственные проверки, которые ловят потерю покупки |
| Переписывать историю Git ради размера | Ломает ссылки и ветки других людей; начать с LFS для новых файлов |
| Мажорные обновления пачкой | Каждая зависимость — отдельный PR с проверками |
| Переносить продукт в шаблон целиком | Шаблон должен быть меньше продукта, иначе он не станет основой |

## 6. Решения, которые нужны от владельца

1. **Офлайн-состав.** Какие картинки и треки должны работать офлайн сразу после установки
   (магазин, галереи, стартовая музыка)? От ответа зависит задача 0.1.
   → **Решено 2026-11-02: как в плане.** В precache — оболочка, картинки слов, минимум иконок
   и стартовый трек. Магазин, техника, галереи и остальная музыка — runtime-кэш при первом
   открытии. Цель — ≤ 3 MiB.
2. **Удаление ангара.** `HangarScene` и `TechScene` не используются. Можно ли удалить (0.4)?
   → **Решено 2026-11-02: удалить** (347 строк; `HangarScene` импортирует `TechScene`,
   `HangarScene` не импортирует никто).
3. **Политика версий.** Устраивает ли автоматизация (1.1) или нужен другой подход?
4. **Защита `main`.** Включены ли обязательные проверки? Проверить в настройках GitHub (сейчас API вернул 403).
   → **Проверено 2026-11-02:** не включены (`protected: false`, rulesets нет), в `slovo2` тоже.
   Включает владелец, см. `05-handoff-new-repo.md`, §8.1.
5. **Судьба сервера.** Пилот, прод или отдельный репозиторий (2.7)?
6. **Мажорные обновления.** Допустимы ли Vite 8, React 19, TypeScript 7 в ближайшие месяцы (2.8)?
7. **Шаблон.** Один монорепозиторий (рекомендация) или отдельный репозиторий для ядра?
8. **Удалённые ошибки.** Нужен ли сбор ошибок у пользователей? Сейчас сознательно нет
   из-за персональных данных детей; если решение меняется, потребуется отдельная оценка ПДн.
9. **Общий origin с `/slovo2/`** *(добавлено при переносе, `05-handoff-new-repo.md`, §8.2).*
   Сайт `/Slovo_Developer/` делит с боевым `/slovo2/` IndexedDB, localStorage и кэши.
   → **Решено 2026-11-02: отдельное хранилище для dev-сборки, отдельной задачей.** Имя базы,
   префикс ключей, канал и кэши задаются переменной сборки. По умолчанию — `slovo2` (прод не
   меняется), в `deploy.yml` этого репозитория — `slovo2-dev`. Это запись состояния, поэтому
   обязательны `test:guard`, `audit:storage` и `tests/vault.test.ts`. Сделать до задач, меняющих
   формат данных (2.1, 2.2).

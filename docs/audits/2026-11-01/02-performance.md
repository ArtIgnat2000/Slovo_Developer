# Аудит 2 — быстродействие, вес доставки и рантайм

**Эксперт:** фронтенд и PWA-производительность · **Оценка:** 2 / 5 по доставке, 3 / 5 по рантайму
**Дата:** 2026-11-01 · **Ветка:** `arena/7cdeb11b-slovo2` · **Итог:** [`00-summary.md`](./00-summary.md)

> **Мнение эксперта.** Рантайм в целом здоров: тяжёлая логика вынесена в чистые функции,
> картинки в WebP, фоновая музыка грузится по требованию. Главная проблема — **вес
> установки и первого экрана**, а не скорость кадров. Precache на 23 МБ противоречит
> собственным комментариям проекта и самой идее «быстрого офлайн-приложения». Вторая
> проблема — модель записи: весь прогресс переписывается при каждом действии. Пока данных
> мало, это незаметно, но это будет расти вместе с объёмом истории.

**Что важно помнить:** в `docs/perf-audit.md` честно сказано, что замеров на телефоне нет.
Этот аудит тоже опирается на **сборку и код**, а не на замеры устройств. Цифры ниже —
размеры файлов и CPU-время в песочнице, а не время загрузки у пользователя.

## 2. Факты (измерено)

### 2.1. Precache service worker

Команда: `npm run build`, затем разбор `dist/sw.js`. Всего **568 записей, 23,12 MiB**.

| Группа | Записей | Размер | Комментарий |
|---|---:|---:|---|
| `products/` | 189 | **9,21 MiB** | магазинные картинки и галереи |
| `audio/` | 2 | **5,06 MiB** | два стартовых трека |
| `cars/` | 57 | 3,95 MiB | машины, салоны, приборные панели |
| `words/` | 260 | 1,34 MiB | картинки слов — **нужны всем** |
| `assets/` (JS, CSS) | 8 | 1,01 MiB | |
| `illustrations/`, `buildings/`, `electronics/`, `planes/`, `icons/`, `ships/`, прочее | 102 | ≈2,3 MiB | |

В `vite.config.ts` сказано: «webp — картинки слов: без них офлайн-режим показывал бы пустые
рамки», «платные треки намеренно НЕ идут в precache», «интерьеры баз… вне precache». То
есть **политика существует**, но **магазинные картинки (`products/`, `cars/`) в precache
попали**: в конфигурации нет исключения для них, а комментарий в блоке `build` прямо говорит, что
«precache PWA должен оставаться маленьким». Противоречие между намерением и результатом.

Для сравнения: `docs/perf-audit.md` фиксировал precache в **753 КиБ**, 110 записей (замер другой
сборки, но порядок величины виден). Объём вырос примерно в 30 раз.

  не загрузка).
- `App.tsx` импортирует все экраны статически: `ShopScreen`, `ParentScreen`, `RatingScreen`,

- В `vite.config.ts` стоит `cssCodeSplit: false`: **весь CSS (214 КБ) один файл**, даже для
  экрана урока.

### 2.4. Модель записи состояния

Конфигурация `useApp` (`src/state/store.ts`, `persist`, `partialize` — `profiles`, `activeId`,
`settings`, `vault`). Проверено в исходниках `zustand` **5.0.15**
(`node_modules/zustand/esm/middleware.mjs`, строки 365–369):

```js
api.setState = (state, replace) => {
  savedSetState(state, replace);
  return setItem();          // вызывается ВСЕГДА, даже если persisted-срез не менялся
};
```

Следствия:

1. **Любое `set` пишет весь прогресс.** Показ тоста (`showToast` → `set({toast})`) сериализует
   всех профилей и кладёт в IndexedDB целиком. `toast` не входит в `partialize`, но запись
   всё равно происходит.
2. **Сейф читает всю прошлую запись на каждой записи.** `src/platform/vault.ts`, `writeOnce`:
   читает предыдущую строку целиком (`getItem`), затем `snapshotDecision` вызывает `readRecord`
   → `JSON.parse(prev)`. Итого на одно действие: чтение строки, парсинг, сериализация стора
   и запись строки в IndexedDB.
3. **Очередь записей сериализует всё.** Это хорошо для корректности (см. `vault.ts`,
   комментарий про «два ответа подряд»), но каждая запись ждёт предыдущую.

### 2.5. Синтетический замер стоимости записи

Скрипт `bench-write-cost.mjs`: профиль с 257
словами, историей дней, сессиями и журналом; замер `JSON.parse` + `JSON.stringify` — то есть
того, что делает один цикл записи, без IndexedDB.

| Сценарий | Размер состояния | Время одной записи (CPU) |
|---|---:|---:|
| ≈1 год дневной статистики, 30 дней сессий (≈1 ребёнок) | 94 КБ | **≈1,1–1,6 мс** |
| ≈10 лет дневной статистики | 331 КБ | ≈3,5–4,5 мс |
| стресс-тест: ≈50 лет дневной статистики, вдвое больше сессий | 1 401 КБ | **≈18–23 мс** |

Линейный рост размера даёт линейный рост времени (≈13–16 мс на мегабайт). Три прогона скрипта дали разброс, поэтому в таблице диапазоны. Синтетика богаче
реального состояния, но зависимость от размера от этого не меняется.

Скрипт лежит рядом с отчётом: `node docs/audits/2026-11-01/bench-write-cost.mjs`. Ядро измерения:

```js
// profile: 257 слов с историей, days: N записей дневной статистики, sessions: S на день
const raw = JSON.stringify(makeState(days, sessionsPerDay));
const N = 200; const t0 = process.hrtime.bigint();
for (let i = 0; i < N; i++) JSON.stringify(JSON.parse(raw));   // ≈ readRecord + сериализация стора
const ms = Number(process.hrtime.bigint() - t0) / N / 1e6;
```

`makeState` — генератор синтетического профиля (см. файл).

Состояние в синтетике богаче реального: в `docs/progress-loss-audit.md` замерено 10,4 КБ за
365 дней. Поэтому сегодня цифра ≈1–1,5 мс, и это **не узкое место**. Но рост линейный, а записей
на одно действие много (тост, ответ, звук, переключение экрана).

### 2.6. Холодный старт

- `src/main.tsx`: `await useApp.persist.rehydrate()` до `ReactDOM.createRoot(...).render(...)`.
  Экран не рисуется, пока не прочитана IndexedDB. Это осознанно (защита от пустого старта),
  но правильно.
- `index.html`: `<div id="root"></div>` пустой. Есть инлайн-скрипт, который ставит тему
  (`data-theme`, цвет фона). **Статического splash-экрана нет**: пока грузятся 1 МБ JS/CSS
  и читается IndexedDB, виден только фон темы.

### 2.7. Рендер React

- `useApp()` без селектора в трёх местах: `StorageScreen.tsx`, `parent/ProgressTab.tsx`,
  `ProfilesScreen.tsx`. Они перерисовываются на любое изменение стора.
- Селекторы `useApp((s) => …)` — 55 вызовов, в целом корректные.
- `React.memo` не используется ни разу. `useMemo` — 8 раз. Это не проблема само по себе,
  но без профилирования нельзя сказать, нужна ли мемоизация.
- Таймеры: в `TaskView.tsx` есть очистка на размонтирование (строка 614). Замечание из
  `docs/perf-audit.md` про «callback после задержки без cleanup» **уже закрыто**.

## 3. Находки

### P1. Precache 23 МБ — самая важная находка

- **Почему важно.** Chrome for Developers прямо отмечает, что precache слишком большого
  объёма тратит трафик пользователя и замедляет установку service worker, а крупные
  ресурсы лучше отдавать через runtime-кэш [1](https://developer.chrome.com/docs/workbox/service-worker-deployment).
  Установка PWA на слабом Android или в мобильной сети — это ≈23 МБ до первого урока.
- **Что делать.**
  1. Исключить из precache `products/`, `cars/`, `ships/`, `electronics/`, `planes/`,
     `buildings/`, `illustrations/` (кроме того, что нужно первому уроку), `docs/`.
  2. Оставить в precache: оболочку приложения, `words/` (1,3 МБ), иконки и один стартовый
     трек (или ни одного — решение владельца).
  3. Для остального — `runtime` с `CacheFirst` и `maxEntries`, как уже сделано для
     `base-tours`, `naash` и `buk3d`.
  4. Убрать `maximumFileSizeToCacheInBytes: 12 MB` — это защита, которая позволяет
     случайно положить в precache крупный файл.
- **Как проверить.** Размер precache до и после; время установки SW на эмуляции
  Slow 4G / 4× CPU; офлайн-сценарий «первый урок после установки»; «магазин после первого
  открытия» работает офлайн из runtime-кэша.
- **Ожидаемый эффект.** Precache ≈2–3 МБ. Установка становится быстрой; вес для магазина
  остаётся, но грузится по требованию.
- **Размер.** S (конфигурация + тесты `test:galleries`, `test:boot`).

### P2. Запись всего стора на каждое действие

- **Почему важно.** Сейчас это ≈1–1,5 мс, но модель не масштабируется: стоимость растёт с
  размером всей истории, а записей много (в том числе чисто визуальных — тосты).
  Для математики, где история попыток станет основным объёмом, это ограничение станет
  реальным.
- **Что делать (быстро, без смены модели).** В `persist` добавить проверку: писать только
  когда изменилась ссылка хотя бы одного из `profiles`, `activeId`, `settings`, `vault`.
  Для `toast` и других UI-полей запись не нужна. Оценка: тост перестанет вызывать
  запись. Это добавляет тест «показ тоста не пишет в IndexedDB».
- **Что делать (целевая модель).** Разнести хранение: профили по ключу `profile:<id>`,
  журнал попыток — append-only таблица с индексом по профилю и дате, настройки и сейф — отдельно.
  Запись одного ответа станет записью одной строки журнала.
- **Ограничение.** В `docs/progress-loss-audit.md` и `perf-audit.md` прямо сказано: **не
  вводить debounce без тестов потери данных**. Любое изменение записи проверять через
  `npm run test:guard`, `npm run audit:storage` и `tests/vault.test.ts`.
- **Размер.** S для быстрой версии; L для целевой модели (план, фаза 2).

### P3. Нет code-splitting; первый экран тяжёлый

- **Почему важно.** Ребёнок, который открыл приложение, чтобы решить урок, скачивает код
  магазина, родительского раздела, рейтинга и диагностики. Точную долю покажет
  визуализатор размеров чанков (см. «Как проверить» ниже): без него её не назвать.
- **Что делать.** `React.lazy` + `Suspense` для `ShopScreen`, `ParentScreen`,
  `RatingScreen`, `VlabsScreen`, `DiagnosticsScreen`, `BukChat` (кроме небольшой заглушки).
  Для CSS — `cssCodeSplit: true` с разделением по экранам, либо вынести редко используемые
  стили. Проверить `vite build` с визуализатором размера чанков.
- **Как проверить.** Размер первого JS (`main` + `modulepreload`) до и после; `test:smoke`
  и `test:boot` (проверяют, что экраны рисуются, в том числе через `Suspense`).
- **Размер.** S–M.

### P4. Один CSS-файл на 214 КБ с неиспользуемыми правилами

- ≈150 классов из `app.css` не встречаются в `src/` (эвристика, см. аудит 1, A4).
- 21 `!important`. `blur` на диалогах и постоянные анимации — по `docs/perf-audit.md`, без
  замеров на слабом GPU.
- **Что делать.** Инструмент поиска неиспользуемых селекторов в CI (с белым списком для
  динамических классов), разбиение по экранам (см. P3), перевод `!important` в
  специфичность, проверка `prefers-reduced-motion` на всех анимациях.
- **Размер.** M.

### P5. Холодный старт без статического экрана

- Пустой `#root` плюс 1 МБ JS: на слабом телефоне в первые секунды виден только фон темы.
- **Что делать.** Статический splash в `index.html` (логотип и фон, без JS), который
  заменяется при монтировании React. Не менять логику `rehydrate` до `render` — это
  защита данных.
- **Как проверить.** Метрика «tap → первый кадр» и «tap → интерактив» на Android Chrome
  с эмуляцией CPU 4×.
- **Размер.** S.

### P6. Лишние перерисовки на `useApp()` без селектора

- Три места подписаны на весь стор. Исправить тривиально: вынести нужные поля в селекторы.
- Перед изменениями — профилирование React DevTools; мемоизацию без измерения не добавлять.
- **Размер.** S.

### P7. Медленный смоук — тормоз разработки

- 148 секунд и 1163 проверки в одном процессе jsdom. Ускорение — разбить на параллельные
  наборы (`node --test` с несколькими процессами), вынести тяжёлые сценарии в браузерный
  тест (см. аудит 3, R2).
- **Размер.** M.

### P8. Замеры на устройствах — отсутствуют (процессный пробел)

- `docs/perf-audit.md` описывает правильный протокол (холодный визит, повторный, авиарежим,
  Slow 4G, 4× CPU, записи tap→карточка). Он **не выполнен**. Без этого все выводы
  выше — гипотезы, подтверждённые кодом и размерами файлов.
- **Что делать.** Выполнить протокол на одном бюджетном Android и одном iPhone; добавить
  Lighthouse CI на `preview`-сборку с порогами для размера precache и первого JS.
- **Размер.** S на выполнение, M на автоматизацию.

## 4. Что уже сделано хорошо

- **Картинки.** WebP; средний размер слова ~4 КБ (замер `docs/perf-audit.md`). Миниатюры и
  галереи загружаются по требованию, есть подложка на время загрузки.
- **Фоновая музыка.** Платные треки не в precache, кэшируются при первом открытии
  (`slovo2-audio`), прогрев ближайших треков — `platform/music.ts`.
- **Runtime-кэши для крупных разделов** (`naash`, `base-tours`, `buk3d`) уже есть —
  это та же модель, которую нужно применить к магазину (P1).
- **Обновления без потери урока.** `startUpdateWatch()` применяет обновление только в
  безопасный момент.
- **Таймеры.** Очистка на размонтирование в `TaskView`.
- **Чистая логика.** Расчёты (`engine/`) не зависят от React — их можно тестировать
  без рендера и измерять отдельно.

## 5. Порядок работ (кратко, подробно — в плане)

1. P1 — precache. *S*, самый большой эффект для установки.
2. P2 (быстрая часть) — не писать на UI-только изменения. *S*
3. P3 — code-splitting. *S–M*
4. P5 — статический splash. *S*
5. P8 — замеры на устройствах до и после. *S*, нужен до всех численных целей.
6. P4, P6, P7 — по мере необходимости.

**Численные цели** предлагаются, владельцу — подтвердить после замеров на устройстве (P8):
precache ≤ 3 МБ; первый JS на 35–40 % меньше (после P3); установка SW — без визуальной
паузы на Slow 4G.

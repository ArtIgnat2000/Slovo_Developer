## 2. Как перенести код в новый репозиторий

Ниже — вариант, который сохраняет полную историю `main` и переносит аудит. Замените `<новое-имя>` на имя
вашего репозитория.

```bash
# 1. Полная копия с GitHub (не из песочницы — там история обрезана)
git clone https://github.com/ArtIgnat2000/slovo2.git slovo2-dev
cd slovo2-dev

# 2. Ветка с аудитом: она основана на main и добавляет только docs/audits/
git checkout -b main-dev origin/arena/7cdeb11b-slovo2

# 3. Создать пустой новый репозиторий (приватный или публичный — на ваш выбор)
gh repo create ArtIgnat2000/<новое-имя> --private --description "СЛОВО 2.0 — разработка и шаблон"

# 4. Отправить как main нового репозитория
git remote add new https://github.com/ArtIgnat2000/<новое-имя>.git
git push -u new main-dev:main

# 5. (по желанию) Старый origin оставить как источник, новый — основной
git remote rename origin upstream
git remote rename new origin
```

Альтернатива без терминала: на GitHub нажмите **Use this template** (если исходный репозиторий помечен как
шаблон) либо создайте пустой репозиторий и загрузите содержимое ветки `arena/7cdeb11b-slovo2`.
Для полной истории предпочтительнее команды выше.

### Что сразу поправить в новом репозитории

Эти пункты найдены в аудите и привязаны к текущему имени репозитория:

1. **`vite.config.ts`, строка `REPO_BASE = '/slovo2/'`.** Если имя репозитория другое, GitHub Pages откроет

2. **GitHub Pages.** В настройках нового репозитория включить Pages с источником «GitHub Actions».
   Workflow `deploy.yml` включает их сам, но только при наличии прав.
3. **Защита ветки `main`.** Включить обязательные проверки из `check.yml` (аудит 3, R4). Сейчас
   проверить через API не удалось (403), в новом репозитории это можно сделать сразу.
4. **Секреты и переменные.** `ADMIN_TOKEN` для пилотного сервера, если он будет нужен, — только в секретах
   Actions или в `compose.env` на сервере. В коде их нет и быть не должно.
5. **Номер версии.** В новом репозитории `release-check` сравнивает версию с `origin/main`. Первый PR

### 8.1. Что включить владельцу в настройках GitHub

**Pages → GitHub Actions.** Settings → Pages → Build and deployment → Source → **GitHub Actions**.
Текущий сайт останется как есть до следующего деплоя из `main`. После переключения перестанет
идти лишний Jekyll-деплой сырых исходников, который запускался рядом с `deploy.yml` на каждый push.

**Обязательные проверки для `main` (ruleset).** Settings → Rules → Rulesets → New ruleset →
New branch ruleset:

1. Ruleset name: `main: обязательные проверки check.yml`; Enforcement status: **Active**.
2. Bypass list: по желанию — **Repository admin**, чтобы в аварийном случае слить PR в обход
   проверок (галочкой при слиянии).
3. Target branches → Add target → **Include default branch**.
4. Rules: **Restrict deletions**, **Block force pushes**, **Require status checks to pass** →
   Add checks → `check` (источник — GitHub Actions). «Require branches to be up to date» можно
   не включать: при параллельных PR версия в `package.json` всё равно даст конфликт.
5. Create.

Если `check` нет в поиске, он появится после первого запуска `check.yml` в PR этого репозитория.
Классическое правило тоже подойдёт: Settings → Branches → Add classic branch protection rule →
`main` → Require status checks to pass before merging → `check`.

### 8.2. Новое решение 9: общий origin с `/slovo2/`

Сайты `https://artignat2000.github.io/slovo2/` и `https://artignat2000.github.io/Slovo_Developer/`
делят один origin. IndexedDB `slovo2` (прогресс и копии), localStorage `slovo2-*`, BroadcastChannel
`slovo2` и runtime-кэши у них общие, раздельны только service worker и precache. Сборка из этого
репозитория, открытая в том же браузере, читает и пишет прогресс сайта `/slovo2/`. Это стоит решить
до задач, которые меняют формат данных (2.1, 2.2), а лучше до первого деплоя расходящейся версии.

Варианты:

- **(а) Отдельное хранилище для dev-сборки.** Имя базы, префикс ключей, канал и кэши задаются
  переменной сборки (например, `VITE_STORAGE_NS`). По умолчанию остаётся `slovo2`, в `deploy.yml`
  этого репозитория ставится `slovo2-dev`. Это изменение записи состояния, поэтому обязательны
  `test:guard`, `audit:storage` и `tests/vault.test.ts`.
- **(б) Не деплоить этот репозиторий на Pages,** пока хранилище не разведено (отключить `deploy.yml`).
- **(в) Отдельный домен для dev:** свой домен для Pages или другой аккаунт или организация GitHub.
- **(г) Оставить общее хранилище намеренно.** Это имеет смысл, если новая версия со временем
  заменит `/slovo2/` для детей: тогда прогресс перейдёт на новый адрес сам. Но до этого момента
  нельзя открывать обе версии в одном браузере, а формат данных нельзя менять без обратной
  совместимости.

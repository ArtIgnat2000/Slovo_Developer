# Аудит 3 — надёжность данных, безопасность, CI/CD и зависимости

**Эксперт:** надёжность и DevOps (SRE / инженер сборки) · **Оценка:** 4 / 5
**Дата:** 2026-11-01 · **Ветка:** `arena/7cdeb11b-slovo2` · **Итог:** [`00-summary.md`](./00-summary.md)

> **Мнение эксперта.** Это самая сильная часть проекта. Потеря прогресса у ребёнка
> разобрана по каналам, каждый канал закрыт кодом и проверен стендом, а не только описан.
> Клиент не содержит типовых XSS-рисков. Слабее всего — **процесс доставки**: правило версий
> мешает работе, деплой не проходит полный набор проверок, а dev-инструменты несут
> высокоуровневую уязвимость при открытом сетевом доступе. Исправляется это быстро и
> дёшево.

---

## 1. Что оценивали

- Надёжность хранения: очередь записей, снимки, откат покупок, чтение до записи.
- Безопасность клиента и пилотного сервера.
- CI/CD: порядок проверок, деплой, защита ветки, версии.
- Зависимости: уязвимости и актуальность.
- Наблюдаемость: диагностика, журналы, сбор ошибок.
- Устойчивость к платформенным рискам (Safari, квоты, eviction).

## 2. Факты (измерено и прочитано)

### 2.1. Хранение

- Одна запись IndexedDB `slovo2` (ключ `slovo2`) плюс снимки `slovo2.snap.{1..3}` и копия
  покупки `slovo2.snap.purchase`.
- Версия схемы `version: 1`, миграция — `normalizePersisted` (санитайзер). Нет списка
  миграций по версиям и нет схем валидации.
- Очередь записей и чтений (`createGuardedStorage`), заморозка при сбое чтения, отчёт о
  результате записи — в отдельный стор, не в сохраняемое состояние.
- Три слота снимков с минимальным интервалом 30 минут; снимок всегда перед «разрушительной»
  записью (`isDestructive`).
- Корзина профилей на 30 дней (`TRASH_MAX = 5` записей), журнал на 40 событий.
- Импорт файла: `JSON.parse(await file.text())`, затем санитайзер. **Лимита размера нет.**

### 2.2. Тесты, которые ловят потерю данных

| Команда | Что проверяет |
|---|---|
| `npm run test:guard` | Копия до списания, откат при сбое записи, баланс после сброса |
| `npm run audit:storage` | Прогон сейфа: копии, корзина, сбой записи (строка «ПОДТВЕРЖДЕНО») |
| `tests/vault.test.ts` | Сейф: копии, корзина, журнал, защита от зацикливания |
| `tests/purchase-guard.test.tsx` | Защита покупок в UI |

Все эти проверки запускаются в CI через агрегатор `test:adaptive` и стенды. Проверено
локально: зелёные.

### 2.3. Безопасность клиента

- `innerHTML`, `dangerouslySetInnerHTML`, `eval`, `new Function` — **0 вхождений** в `src/`.
- Единственный `fetch` в `src/` — загрузка аудиофайла (`platform/music.ts`).
- Внешние ссылки открываются с `rel="noopener noreferrer"`.
- Сторонних скриптов и аналитики нет. Сборка не отправляет данные ребёнка никуда.
- Адрес поддержки (ссылка на СБП-перевод) захардкожен в `src/` — для шаблона лучше вынести в конфигурацию.

### 2.4. Пилотный сервер (`server/`)

- Токены хранятся как SHA-256 (`token_hash`, `sha256(token)`), сравнение админ-токена —
  через `safeEqual` (хеши и `timingSafeEqual`). Минимальная длина `ADMIN_TOKEN` — 24 символа.
- Лимит тела запроса 64 КБ; заголовки `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer`.
- Телеметрия — белый список из 14 событий; текст ответов не хранится, только факт верно/неверно.
- Лимиты запросов — **в памяти процесса** (`buckets`, фиксированное окно). Сбрасываются при
  перезапуске и не работают на нескольких экземплярах.
- `X-Forwarded-For` учитывается только при `TRUST_PROXY=1`.
- Образ `node:22-alpine`, пользователь `app` (не root). Тег без digest-пина.
- Клиент **не обращается к серверу**: единственный сетевой вызов — загрузка музыки. Пилот
  изолирован, что соответствует `docs/proposals/backend-social-plan.md` («предложение, не реализовано»).

### 2.5. CI/CD

- `.github/workflows/check.yml` (на PR в `main`): сначала `test:release` и `release:check`,
  затем `npm ci`, далее 11 проверок, затем `build` и `test:boot`. Порядок разумный: быстрые
  проверки первыми.
- `.github/workflows/deploy.yml` (на push в `main`): `audio:check`, `content:check`,
  `test:smoke`, `build`, затем деплой на GitHub Pages. **Не запускаются:** `typecheck`,
  `test:guard`, `test:icons`, `test:contrast`, `test:galleries`, `server:test`, `test:boot`.
- `.github/workflows/fetch-music.yml` — ручной и по изменению файла, пишет в ветку. Есть `concurrency`.
- **Статистика последних 30 запусков `check.yml`** (`gh run list`): 21 успех, 9 падений.
  **Все 9 — на одном шаге:** «Require a new release for every PR».
- Защита ветки `main` **проверить не удалось**: API вернул 403. Нужно посмотреть в настройках
  GitHub, включены ли обязательные проверки.

### 2.6. Зависимости

| Проверка | Результат |
|---|---|
| `npm audit --omit=dev` | **0** уязвимостей |
| `npm audit` (включая dev) | **15**: low 3, moderate 9, high 3 |
| Высокие (high) | `vite` 5.4.21 (прямая, диапазон ≤6.4.3), `source-map-js`, `undici` (транзитивные) |
| `npm outdated` | `vite` 5.4 → 8.3; `react` 18.3 → 19.3; `vite-plugin-pwa` 0.21 → 2.0; `typescript` 5.9 → 7.0; `@vitejs/plugin-react` 4.7 → 6.1 |

Все уязвимости высокого уровня — в **dev-цепочке**, в production-бандл не попадают. Но
`vite` — это dev-сервер, и у него в конфигурации включено:

- `server.host: '0.0.0.0'` и `preview.host: '0.0.0.0'` — сервер слушает все интерфейсы
  (локальная сеть, а не только машина разработчика);
- `allowedHosts` включает `.ngrok.io` и `.trycloudflare.com` — туннели наружу.

Сочетание «уязвимый dev-сервер + открыт в сети + разрешены туннели» — это поверхность атаки,
которую стоит закрыть по умолчанию.

### 2.7. Наблюдаемость

- `src/platform/diagnostics.ts` — локальная диагностика: состояние сейфа, снимков, персистентности.
- Удалённого сбора ошибок нет. Это **осознанное решение по персональным данным детей**,
  но его стоит закрепить в документации, иначе следующий разработчик добавит Sentry «по привычке».
- Сервер пишет структурированные JSON-логи и журнал `audit`.

### 2.8. Платформенные риски

- **Safari (iOS).** Без установки на домашний экран WebKit удаляет script-writable хранилище
  сайта после 7 дней без взаимодействия с сайтом; приложения на домашнем экране исключены
  [2](https://progressivewebapps.com/platforms/ios-safari/). В проекте это уже учтено: есть
  экран хранилища, `checkPersistence`, `requestPersistence` по жесту, подсказка об установке
  (`install-hint.test.tsx`).
- **Квоты и постоянное хранилище.** `navigator.storage.persist()` запрашивается по жесту
  родителя, статус показывается — правильно.

## 3. Находки

### R1. Версионирование данных: нет миграций и схем (высокий риск для шаблона)

- Версия `version: 1` неизменна с первого релиза. `migrate` сводится к `normalizePersisted`,
  то есть каждая новая форма данных обрабатывается ручными `normalize*`-функциями
  (около 25 в `store.ts`, `engine/` и `platform/`).
- Нет списка миграций «с версии N на N+1», нет тестов на старые выгрузки как обязательной
  части изменения. Это работает, пока разработчик помнит все места, где нормализуется поле.
- **Рекомендация.** Список миграций по версиям (`migrations[n]`), тесты «выгрузка версии N
  читается текущей сборкой» (фикстуры старых выгрузок в `tests/fixtures/`), схема валидации
  (Zod или Valibot) для импорта и профиля. Это уменьшит риск потери данных при изменении
  модели, и для шаблона это обязательная часть.
- **Размер.** M.

### R2. Нет браузерных end-to-end тестов (средний риск)

- Все проверки идут в jsdom с `fake-indexeddb`. Это не воспроизводит: квоты, eviction,
  поведение IndexedDB в Safari и Chrome (например, транзакции при закрытии вкладки),
  service worker, установку PWA, работу офлайн.
- `docs/perf-audit.md` прямо говорит, что jsdom не проверяет сеть, декодирование, SW.
- **Рекомендация.** Playwright по прод-сборке (`npm run preview`) с 4–6 сценариями:
  первый запуск, урок до конца, покупка и откат, офлайн после установки SW, обновление
  при открытом уроке, импорт выгрузки. Запуск по расписанию или на PR с метками.
- **Размер.** M.

### R3. Потеря данных у пользователей Safari без установки (платформенный риск)

- Это не дефект кода, а свойство платформы (см. 2.8). Приложение уже предупреждает и
  предлагает установку.
- **Что уже есть.** Напоминание «Сохраните файл: прогресс хранится на этом устройстве» —
  если последняя копия старше 14 дней (`EXPORT_REMINDER_MS` в `engine/vault.ts`). Но оно видно
  только тому, кто открыл «Родителям → Прогресс». Ребёнок или родитель, который пользуется
  приложением в Safari и не заходит в раздел, его не увидит.
- **Рекомендация.** Показывать напоминание о копии на главном экране для родительского
  профиля (или при первом запуске после 14 дней без копии) и проверить в E2E (R2), что оно
  появляется в Safari-режиме без установки на домашний экран.
- **Размер.** S.

### R4. Деплой не проходит полный набор проверок (средний риск)

- `check.yml` запускает весь контур, но только на PR. `deploy.yml` на push в `main`
  запускает подмножество (см. 2.5). Если ветка `main` не защищена обязательными проверками,
  в неё может попасть коммит без `typecheck`, `test:guard` или `test:boot`.
- **Рекомендация.** Вынести полный контур в переиспользуемый workflow (`workflow_call`) и
  сделать `deploy` зависимым от него (`needs`). Включить обязательные проверки в настройках
  `main` (владельцу репозитория — проверить сейчас).
- **Размер.** S.

### R5. Правило версий ломает CI почти в трети случаев (высокий риск для процесса)

- 9 из 30 последних запусков упали на «Require a new release for every PR». Это не
  ошибки кода, а забытые шаги: версия, lock, заметка, заголовок PR.
- Версия в `package.json` и `package-lock.json` — общий файл, и при параллельных PR
  возникают конфликты. Инструкция в `README.md` описывает семь ручных шагов.
- **Рекомендация.** Автоматизировать: release-please или changesets. Смысл правила
  («каждое изменение — отдельный релиз») сохраняется, а ручная работа уходит. Цель:
  0 падений из-за версии в течение 20 PR.
- **Размер.** M. Снимает главный источник «красного» CI.

### R6. Dev-зависимость с высокой уязвимостью и открытый dev-сервер (высокий риск безопасности)

- `vite` 5.4.21 — high (диапазон ≤6.4.3). Production не затронут (`--omit=dev` — 0), но
  разработчик и CI работают с этим инструментом.
- `server.host` и `preview.host` — `0.0.0.0`, `allowedHosts` включает туннели.
- **Рекомендация.**
  1. Обновить `vite` до версии с исправлением; плагин `vite-plugin-pwa` и `@vitejs/plugin-react`
     проверить на совместимость (это отдельная задача, см. план).
  2. По умолчанию слушать `localhost`; открывать сеть только по явному флагу
     (например, `VITE_LAN=1`). Превью для песочницы оставить через отдельный скрипт.
  3. Транзитивные high (`undici`, `source-map-js`) — обновлением зависимостей, которые их тянут.
- **Размер.** S–M.

### R7. Пилотный сервер: изоляция и платформенные риски (средний риск, зависит от решения)

- Сервер не подключён к клиенту. Это правильно для пилота, но означает, что код поддерживается
  без обратной связи.
- `node:sqlite` в статусе release candidate (Stability 1.2); в последних версиях Node класс
  уже переименовали [3](https://cnayanajith.com/blog/node-sqlite). Версия Node фиксирована
  только тегом `22`.
- Лимиты запросов в памяти — не работают при нескольких экземплярах и сбрасываются при перезапуске.
- **Рекомендация.** Решить судьбу пилота (план, фаза 2, задача 2.7). До решения: зафиксировать
  версию Node полным тегом или digest, вынести rate limit в SQLite или заголовки прокси,
  добавить `docker scout`/аналог в CI.
- **Размер.** S (фиксация версий), M–L (если пилот переходит в прод).

### R8. Импорт без ограничения размера (низкий риск)

- `JSON.parse(await file.text())` на файл любого размера. Санитайзер защищает состояние,
  но не браузер: большой файл замораживает вкладку.
- **Рекомендация.** Лимит размера (например, 5 МБ) с понятным сообщением до разбора.
- **Размер.** S.

### R9. Устаревание основных зависимостей (средний риск, плановый)

- React 18 (19 вышел), Vite 5 (8 вышел), `vite-plugin-pwa` 0.21 (2.0), TypeScript 5.9 (7.0).
- Это не срочно, кроме `vite` (R6). Но каждая отложенная мажорная версия увеличивает стоимость
  перехода. Шаблон должен стартовать с актуальных версий.
- **Рекомендация.** Отдельные PR на мажорные обновления, каждый — с `test:smoke`, `test:boot`
  и `test:galleries`. Порядок: Vite и плагины → React → TypeScript.
- **Размер.** M–L, по частям.

### R10. Захардкоженные значения, которые должны быть конфигурацией (низкий риск)

- `REPO_BASE = '/slovo2/'` в `vite.config.ts` (уже есть `VITE_BASE`), адрес поддержки, TG-ссылка,
  `TZ=Europe/Moscow` в Dockerfile, имя проекта в манифесте.
- **Рекомендация.** Собрать в один файл `project.config.ts` — для шаблона обязательно.
- **Размер.** S.

## 4. Что уже хорошо

- **Порядок проверок в `check.yml`** — быстрые первыми; `release:check` стоит до `npm ci`,
  и это осознанное решение после PR #140.
- **Разбор каналов потери данных** (`progress-loss-audit.md`) — образцовый: факты, сценарии,
  стенды, план, решения. Это то, что нужно повторять в шаблоне.
- **`npm run pickup`** — одна команда для восстановления рабочей копии. Удобно, но её
  стоит описать для людей, а не только для агента (см. аудит 1, A6).
- **Сервер** — безопасные умолчания: токены хешами, `no-store`, белый список событий,
  не-root в Docker, тесты контракта.
- **Политика обновлений PWA** — не перезагружать посреди урока; это снижает риск
  потери незавершённой сессии.

## 5. Порядок работ (кратко, подробно — в плане)

1. R6 — обновить `vite` и закрыть dev-сервер по умолчанию. *S–M*, безопасность.
2. R5 — автоматизация версий. *M*, снимает красный CI.
3. R4 — полный контур на деплое, защита `main`. *S*.
4. R1 — миграции и схемы; обязательно до любых изменений модели (фаза 2).
5. R2 — E2E в браузере. *M*
6. R7, R8, R10 — по мере необходимости. R9 — плановые мажорные обновления.
